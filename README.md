## The problem

The Argentine state publishes the same procurement twice: as a notice in the
*Boletín Oficial* (the Official Gazette), written by the agency, and as a
structured record in the open-data portal. **Nobody checks that they say the same
thing.**

A supplier who goes by the notice and an auditor who goes by the registry can be
looking at two different versions of the same call.

## What it does

For each notice in the Gazette, the agent:

1. **Extracts** nine fields from the text with a model.
2. **Builds the lookup key** and finds the corresponding process in the official
   registry.
3. **Decides whether it is even the same process** before comparing anything,
   using three independent signals and an explicit threshold. Below the
   threshold it escalates to human review instead of inventing a finding.
4. **Compares** only the fields that were not used for matching, and
   distinguishes four outcomes: match, discrepancy, the Gazette omits it, or not
   comparable.

With a trace of every step, an audit log, enforceable permissions, a spend cap
checked **before** each call, retries on transient errors, and resumability.

## The ground truth is not generated by a model

Two yardsticks, neither produced by a model:

- **The state's official registry** (128,951 COMPR.AR records) is the yardstick
  for the *finding*. It is public, it is at scale, and it exists independently of
  this project.
- **Project 01's hand-labeled set of 115 notices**, with the ceiling of the
  experiment measured by blind double-labeling, is the yardstick for the
  *system*. It makes it possible to measure how much the full pipeline degrades
  when the extractor gets things wrong.

**Project 02's ground truth did not cost a single new label: project 01 is the
oracle for project 02.**

## The data contract is verified before anything is built

The OCDS standard, which the Argentine portal uses, **defines no field for the
administrative file number**: its identifier is `convocatoria_id`. The Gazette
publishes `expediente` and `numero_procedimiento`. That the two sides could be
joined was a hypothesis, not a fact.

`src/verificar_cruce.py` put it to the test before a single line of the agent was
written. It discovers the CSV's schema on its own, detects candidate key columns
by the **shape** of their values rather than by their names, tries each join and
reports the rate.

**The decision criterion was written down before the script was run**, so the
goalposts could not be moved after seeing the result:

| Join rate | Decision |
|---|---|
| ≥ 60% | the project goes ahead |
| 30–60% | goes ahead, with coverage declared |
| < 30% | there is no join → plan B |

Result: **the project goes ahead, with coverage declared.** Plan B — a temporal
state agent, resting on the fact that the Gazette itself publishes postponements
and corrections that supersede earlier notices — was designed and never needed.

**An unvalidated instrument returns a false verdict.** The first join came back
at 9% and we nearly scrapped the project. The error was in the verifier, not in
the data: the dominant form of `Numero_Proceso` is `340/1-0006-LPR17` — the
procurement unit code contains a slash — and the regular expression only accepted
the slash-free form, discarding 59% of the 128,951 records.

## Results · full corpus

`python src/agente.py` over the corpus's **267 calls for bids**, then
`src/reprocesar.py` so that all 267 are evaluated with the same version of the
code:

| | | |
|---|---:|---|
| **Matched and compared** | **95 · 36%** | verified |
| Uncertain → human review | 11 · 4% | the system does not decide alone |
| Has a key, no record loaded | 35 · 13% | the portal publishes with a lag |
| No procurement unit code in the notice | 126 · 47% | the agency does not use COMPR.AR: **no structured record exists** |

### The format decides — and so does the publication date

| Notice format | Calls | Verified | |
|---|---:|---:|---:|
| COMPR.AR | 143 | **94** | **66%** |
| Free-form | 124 | 1 | 1% |

That 66% hides the most interesting thing in the project. Split by edition of the
Gazette:

| Edition | COMPR.AR notices | Verified | No record | Rate |
|---|---:|---:|---:|---:|
| 2026-06-01 | 29 | 25 | 2 | 86% |
| 2026-06-19 | 24 | 19 | 0 | 79% |
| 2026-07-01 | 15 | 14 | 0 | 93% |
| 2026-07-20 | 34 | 34 | 0 | **100%** |
| **2026-08-03** | **41** | **2** | **30** | **5%** |

**The method works at between 79% and 100% on every edition the registry has
caught up with. Excluding 2026-08-03: 92 of 102, or 90%.** The August 3 edition
collapses because the open-data portal only holds data through July.

And that turns the publication lag into a finding with a number of its own:
**two and a half months after that edition was published, 73% of its processes
were still not loaded in the state's open-data portal.** This is not a defect of
the project — it is a fact about the system's transparency, and it has to be kept
separate from the 47% of agencies that simply do not use COMPR.AR.

The same boundary by format shows up in project 01, measuring something else
entirely: there the human extraction ceiling was 98.7% on COMPR.AR notices and
72.7% on free-form ones. Two projects, two methods, the same structural crack.

### The discrepancies

Fields that do **not** take part in the matching, so a difference here is a
finding and not an artifact of how the candidate was chosen:

| Field | Differs | Reading |
|---|---:|---|
| `tipo_procedimiento` | 0 / 95 | always agree |
| `monto_estimado` | 0 / 95 | never differ… because the notice never carries it |
| **`fecha_apertura`** | **15 / 95 · 16%** | **the published date is not the registry's** |

The fifteen shifts, in days:

```
-16, +3, +6, +8, +10, +11, +12, +14, +15, +15, +17, +18, +18, +19, +20
```

**Fourteen forward and one backward.** Median +14, mean +11.3.

The fourteen that move forward are **postponements** that the registry reflects
and the published notice does not: the bid opening was moved and the legally
binding publication went stale.

The one that moves backward (`53176-26`, −16 days) **is the worst of the fifteen
for a bidder.** The notice is published on 2026-07-31 announcing an opening on
08-19; the registry says it opened on 08-03. A postponement gives you more time
than you thought. This takes it away: you prepare for the 19th and the opening
already happened. The match is solid — identical object, single candidate,
confidence 1.0 — so it is not a join error.

**And here is a lesson about method that is worth more than the number.** Over
the 50 notices in the hand-labeled subset, all ten shifts went *forward*, and
this README asserted "never backward." With the 95 of the full corpus the
opposite case appeared. **The small sample supported a stronger claim than the
complete data supports.** That is what enlarging a sample is for, and the claim
was corrected rather than defended.

### The coverage gap, which is not the same thing

| Field | The notice omits it and the registry has it |
|---|---:|
| `monto_estimado` | **95 of 95 · 100%** |
| `fecha_apertura` | 14 of 95 · 15% |

The registry publishes budgets in the hundreds of millions of pesos that the
notice does not carry. Whoever reads the Gazette cannot know the budget for the
call; whoever reads the open-data portal can. These are two publications by the
same state with different levels of transparency, **and it is reported separately
from the discrepancies on purpose**: mixing them inflates the finding with
something that is nobody's error.

## The agent against human ground truth

This is the part almost no project with a model measures. Over the 115
hand-labeled notices, `src/cruzar.py` performed the same matching starting from
the labels; the agent did it extracting on its own. Comparing the two runs
measures **how much the complete system degrades when the extractor makes
mistakes** — which is not the same thing as the extractor's accuracy.

| | |
|---|---:|
| Same decision as with perfect labels | **114 / 115 · 99%** |
| Same registry process selected | **50 / 50 · 100%** |
| Same date discrepancies detected | **10 / 10** |
| False positives | **0** |

**The single difference is the agent escalating to human review** a notice the
labels had given up on: confidence 0.539 against a threshold of 0.55. That is not
degradation, it is the safe behavior — and it is reported as such instead of
hiding inside the 99%.

**Why this metric and not extraction accuracy.** The same accuracy produces very
different degradations depending on which field the error lands in. An error in
`objeto` lowers the confidence and the case carries on; an error in
`numero_procedimiento` breaks the key and throws the whole case away. No
extraction eval measures that, and it is the only thing that matters to whoever
operates the system.

### What it costs to operate

Over the 267 calls for bids:

| | |
|---|---:|
| Total cost | **USD 0.1970** |
| Cost per notice | **USD 0.000738** |
| Cost per 1,000 notices | USD 0.74 |
| Tokens | 205,590 in · 54,147 out |
| Median / p95 latency | 3.3 s / 4.3 s |
| **Extraction failures** | **0 of 267** |

Against the human baseline measured in project 01 — 113 s and USD 0.058 per
document, with the human cost anchored to the statutory minimum wage: **28×
faster and 79× cheaper.** The speed figure uses wall-clock time per document
(4.1 s, including the waits imposed by rate limits), not the model's latency,
because that is what someone operating this would actually experience.

The model (`gemini-3.5-flash-lite`) was not chosen here: it is project 01's
measured conclusion, where the model five times more expensive did not justify
its price.

Zero failures in 267 calls is not luck: Google's free tier allows 15 calls per
minute and the run hit that ceiling several times. The retries with exponential
backoff on transient errors recovered every one of them.

## What this taught project 01

**The model found an error in the hand-labeled gold set.** Notice `44538-26` was
labeled with an opening date of `3/07/2026`; the text says `13/07/2026`. A typo.
That made the analysis report a +10-day postponement that did not exist.

Having found one, you have to ask how many more there are. The matched notices
were audited with a deterministic reader of the `Acto de Apertura` block — no
model calls, zero cost:

| | |
|---|---:|
| With a machine-readable block | 29 |
| Wrong labels | **1** |
| Wrong model extractions | **0 of 29** |
| Without the block (free-form): not auditable | 21 |

The correction is logged in
[`docs/CORRECCIONES.md`](https://github.com/enzoestevez/eval-extraccion-licitaciones/blob/main/docs/CORRECCIONES.md)
in project 01, with an explicit rule: **a label is corrected only if the text of
the document contradicts it, never because a model says otherwise.** The model is
not the source of truth; what it can do, and did here, is point at where to look.

**Project 01's 85.7% ceiling was not corrected.** That number measures human
consistency, and this typo is precisely one of the inconsistencies the blind
double-labeling existed to detect. Removing it would be cheating with the
measurement: the ceiling is low, in part, exactly because a tired human writes
`3/07` where the document says `13/07`.

## How six bugs were found without spending a single call

The first run reported **zero discrepancies**, with `fecha_apertura` "omitted by
the Gazette" in **100%** of matched cases.

A number that looks too clean is not a finding, it is a clue. **Zero
discrepancies was not "I found nothing" — it was "I compared nothing."** Pulling
that thread surfaced six bugs, all six in my own code and none in the model:

| | Bug | Effect |
|---|---|---|
| 1 | `n_fecha` could not parse `2026-06-08T09:00:00` (with seconds) | the field carrying the central finding came out `None`. **The model had extracted that date correctly in 98 of 115 cases** |
| 2 | `llave()` demanded `NN/YYYY` and rejected `38/12-0197-LPU26` | the model was answering **correctly** and returning **more** information than asked for |
| 3 | `n_uoc` kept `UOC: 392/000` as `392/0` | of the registry's 128,951 unit codes, **zero** have an all-zeros segment: keeping it guaranteed never matching |
| 4 | `RX_UOC_TEXTO` required the colon and did not see `UOC 118-00` | confusing "has no unit code" with "I failed to read it" was being counted as a finding about the state, and it was my own bug |
| 5 | `n_monto` read `2.797` as 2.8 | in Spanish the period is the thousands separator |
| 6 | `tipo_procedimiento` compared two different vocabularies | the registry uses a closed list of 6 values, the Gazette writes free text: `Subasta Pública` against `Subasta` was reported as a discrepancy |

**Result of the six fixes, over the 115 labeled notices:**

| | before | after |
|---|---:|---:|
| Verifiable | 39 / 115 · 34% | **50 / 115 · 43%** |
| "The registry has not loaded it" | 12 | **3** |
| `fecha_apertura` differs | 7 · 18% | **10 · 20%** |
| False positives | 2 | **0** |

What I was counting as "the state did not load the process" was, in nine cases,
my own code failing to read a unit code.

### The design that made this free

A pipeline with a model in it has two halves with opposite properties:

```
the model call        expensive · slow · non-deterministic · rate-limited
everything after it   free · instantaneous · deterministic
```

The trace stores the `extraido` field: exactly what the model returned for each
case. `src/reprocesar.py` re-runs the deterministic half over those extractions
with the current code. **The six fixes were each verified at USD 0.00**, when
re-running the whole agent cost USD 0.20 and half an hour per attempt.

That is why `procesar()` is split into `extraer()` and `decidir()`: **the border
between what is expensive and what is reproducible sits on a single line, on
purpose.**

And it solved a problem we had not anticipated: the first 115 cases ran with the
old logic and the remaining 152 with the fixed one. Reporting over that trace
would have mixed two versions of the code into one number — the kind of error
nobody catches until someone compares them in an interview. `reprocesar.py` left
all 267 evaluated with the same version, without paying for a call.

`reprocesar.py` **does not touch** `reports/traza.jsonl`. That is the trace of
what the agent did — an audit log — and rewriting it to say something else is
exactly what an audit log must not allow. The reprocessing goes to a new file and
records which commit and which threshold it ran with.

## Architecture

```
notice from the Gazette (text)
   │
   ├─ src/agente.py ── extraer() ──► model ──► 9 fields + confidence
   │       │                          └─ retries on 429/503/timeout
   │       │                          └─ spend cap checked BEFORE the call
   │       │                          └─ dry-stop if 3 fail in a row
   │       │
   │       └─ decidir() ─── the deterministic half, replayable for free
   │             │
   │             ├─ key:  unit code + number + year  ->  84/129-0362-LPU26
   │             │     also accepts the registry's full process number
   │             │
   │             ├─ candidates (the key is NOT unique:
   │             │   111,452 keys for 128,951 records)
   │             │
   │             ├─ CONFIDENCE — is it the same process?
   │             │     object 0.55 · chronology 0.30 · uniqueness 0.15
   │             │     < 0.55 -> human review, nothing gets compared
   │             │
   │             └─ COMPARISON of fields not used for matching only
   │                   match | differs | omitted by the Gazette | not comparable
   │
   ├─ reports/traza.jsonl       audit log, append-only, with `extraido`
   ├─ reports/auditoria.jsonl   one line per decision
   │
   ├─ src/reprocesar.py ──► traza-reproceso.jsonl   (USD 0.00)
   └─ src/informe.py ─────► reports/agente.md

src/comun.py is the shared core: normalizers, the registry index, the key, the
confidence score and the comparison. The analysis (cruzar.py) and the system
(agente.py) use EXACTLY the same logic — zero duplicated functions. If each had
its own copy, their numbers would diverge with the first change and nobody would
notice until someone compared them.
```

## What this does not solve

- **47% of notices have no counterpart.** Universities, the central bank, Banco
  Nación, the public prosecutor's office and multilateral lenders publish in the
  Gazette but do not use COMPR.AR: **for almost half the calls there is nothing
  to verify against**, and that is exactly where the extraction matters most.
- **13% have a key but the registry has not loaded the process**, and it is
  concentrated in a single edition (30 of 35 are from August 3). That makes the
  global 36% understate what the method can do while also measuring something
  real about the portal. Both numbers are reported separately and neither
  replaces the other.
- **The free-form notices among the matched ones could not be audited against the
  text**: they have no `Acto de Apertura` block readable by a deterministic rule.
  Declared, not solved.
- **The corpus is 267 calls from 5 editions of 2026.** Enough to measure
  degradation and coverage by format, too little to claim a national rate. The
  16% discrepancy figure is an order of magnitude, not a precise number.
- **The directional asymmetry is the most fragile result.** With 50 cases it was
  10 of 10 forward; with 95 it was 14 of 15. The tendency toward postponement
  holds, the "never backward" does not.
- **The matching confidence uses the registry's `fecha_apertura` against the
  notice's publication date**, and `fecha_apertura` is then reported as a
  finding. They are different quantities — the extracted opening date is never
  touched — so there is weak coupling, not circularity. It is declared rather
  than hidden.

## Decisions I made, and why

- **The data contract gets verified first.** The join is not guaranteed by any
  standard: measuring it costs an hour, building on an assumption costs a week.
- **The input is copied, not referenced.** A repo that needs an unversioned
  sibling folder cannot be cloned or reproduced. The copy travels with its
  provenance and its date.
- **The agent decides whether it is looking at the same process before comparing
  fields.** In `36208-26` the notice says public tender for dairy products and
  the registry says private tender for maintenance supplies, with an opening date
  **earlier** than the notice's publication. That is not a discrepancy, it is a
  wrong match. Comparing without a prior confidence score **invents findings**,
  and a system that invents findings is worse than one that finds none. This
  decision came out of the verification data, not out of an upfront design.
- **A field used for matching cannot be reported as a finding.** The first
  version used `tipo_procedimiento` in the confidence score and then reported 0%
  discrepancy on that field. It was circular by construction. It is out of the
  weights now, and the code marks each field as `reportable` or not.
- **The amount does not count as a discrepancy when the notice does not carry
  it**, and an amount in another currency is not compared at all: `USD 2.797`
  against the registry's `2797,00` look like the same figure and are not. That
  case is marked `no_comparable` instead of picking one of the two readings.
- **A suspiciously clean number gets investigated before it gets reported.** Zero
  discrepancies over 36 cases was a bug of my own, not a finding. It is the
  methodological decision that produced the most value in the whole project.
- **Coverage is split by edition before any average is reported.** The 66% on
  COMPR.AR notices hides four editions between 79% and 100% and one at 5%.
  Averaging that would have concealed both the method's capability and the
  portal's lag.
- **The model was not chosen here.** `gemini-3.5-flash-lite` is project 01's
  measured conclusion. And the version is pinned in `requirements.txt`: a
  benchmark run is not compared against a `latest` that shifts under your feet.
- **Errors that affect every case are not logged per case.** The first run wrote
  the same error five times because a package was missing. Now a pre-flight check
  verifies the key and the package once before the loop, and a dry-stop aborts if
  three fail in a row with no successes.

## The chain

This is part 2 of three projects where **each one builds the instrument that
measures the next**, so no ground truth anywhere in the chain is generated by a
model.

| | Project | What it is for the next one |
|---|---|---|
| 1 | [eval-extraccion-licitaciones](https://github.com/enzoestevez/eval-extraccion-licitaciones) — evaluation harness | the oracle for this project |
| **2** | **this one** — verification agent | the system under test for project 3 |
| 3 | [auditoria-adversarial-agente](https://github.com/enzoestevez/auditoria-adversarial-agente) — adversarial audit | the reproducibility check that validated this project |

And the traffic runs both ways: this project's model found the typo in project
01's gold set, and project 3 found that **this project's deterministic oracle
(`cruzar.py`) is more vulnerable to input variation than the model-based agent it
validates** — a legitimate spelling of one field defeats the regular expression
and not the model.
